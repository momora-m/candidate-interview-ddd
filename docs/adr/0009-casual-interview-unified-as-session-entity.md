# ADR-0009: カジュアル面談（Casual Interview）の選考セッションエンティティ統合モデリング方針

- **ステータス**: 承認 (Accepted)
- **決定日**: 2026-10-18

## コンテキスト (Context)
転職活動において「カジュアル面談」は、一般的な1次・2次・最終面接とは異なり、以下の特徴を持つ：
- 企業側から一方的に合否（通過 / お見送り）を下される場ではなく、候補者と企業の双方がカルチャーや期待値をすり合わせる相互理解の場である。
- 実施時点では、ポジションや志望動機が具体化していない（オープンポジションや情報収集段階の）ケースが多い。

一方で、候補者（求職者自身）の時間管理および事前・事後の行動という観点で見ると、以下の通りドメイン上の不変条件と振る舞い（Invariants / Behavior）は面接と共通している：
1. **時間枠の拘束**: 特定の `TimeWindow`（日時区間）を占有する。
2. **日程衝突の防止**: 他社の確定面接や移動バッファとの重複は絶対に許容されない（ダブルブッキングの禁止）。
3. **事前準備と質問**: 企業リサーチを行い、逆質問を持参して対話に臨む。
4. **事後振り返り**: 面談後に企業の印象スコアやメモ（`InterviewReflection`）を記録し、今後の志望度を判断する。

これらを別々のエンティティ（例: `CasualMeeting` と `InterviewSession`）に分離した場合、スケジュール衝突判定ドメインサービス、ToDo自動生成、カレンダー表示、DB永続化スキーマが2系統に分裂し、不要な重複とモデルの貧弱化を招く懸念があった。

## 決定事項 (Decision)
**カジュアル面談を独立したエンティティとしては分離せず、同一の `InterviewSession` エンティティとして統合モデリングする** 方針を採用した。

具体的には以下の設計とする：
- **ステージ属性による識別**: `SelectionStage` の値オブジェクトに `CASUAL_INTERVIEW`（順序: 2）を定義し、セッションがカジュアル面談であることを表現する。
- **オプショナルな応募情報**: カジュアル面談の段階を考慮し、`JobApplication` の応募ポジション詳細や志望動機（`PositionMotivation`）は初期状態でオプショナル（未設定またはドラフト）であることを許容する。
- **ライフサイクルと意思決定の差別化**:
  - セッション自体のデータ構造は共通とするが、面談完了後の集約の状態遷移ルールを区別する。
  - 選考面接が「企業からの合否連絡待ち」を前提とするのに対し、カジュアル面談完了後は**「候補者自身が正式選考へ進むか、見送るか」を意思決定するフェーズ**として扱う（振り返り入力後、候補者主導で `FIRST_TECHNICAL` 等のステージへ前進、または選考辞退 `WITHDRAWN` を選択）。

## 影響とトレードオフ (Consequences)
- **メリット**:
  - `CandidateScheduleConflictDomainService` による日程重複・移動バッファ衝突判定を、カジュアル面談に対しても共通のルールで漏れなく適用できる。
  - 逆質問の不変スナップショット割当（ADR-0004）、事前準備ToDo自動生成、事後振り返り（Reflection）の仕組みを二重実装することなくそのまま活用できる。
  - モデルの概念数が抑えられ、コードベースおよびDBスキーマがシンプルに保たれる。
- **トレードオフ**:
  - 応募前（受けるか完全に決まっていない接点段階）であっても、システム上は `JobApplication`（Stage: `CASUAL_INTERVIEW`）を作成して管理する必要がある（「企業に対する選考・接点プロセス」として包括的に捉えるユビキタス言語の統一が必要）。
